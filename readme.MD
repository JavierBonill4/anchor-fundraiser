# Token Fundraiser

An Anchor program for time-limited SPL Token fundraising campaigns. A maker
chooses the mint, target, duration, beneficiary, and optional organizer fee;
contributors deposit tokens into a vault controlled by the fundraiser PDA.

## Prerequisites

| Tool       | Version                                      |
| ---------- | -------------------------------------------- |
| Anchor     | 1.1.2 (`avm install 1.1.2 && avm use 1.1.2`) |
| Solana CLI | 3.1 or newer                                 |
| Node       | 20 or newer, with `yarn`                     |

```bash
yarn install
anchor build
anchor keys sync   # first time only
yarn test
```

The repository does not ship its program keypair. On the first build, Anchor
generates one; `anchor keys sync` updates `declare_id!` and `Anchor.toml` to
match it. Run the command once and rebuild.

`cargo-build-sbf` defaults to SBPF v0, but the Anchor 1.1.2 program generated by
this toolchain must be executed as SBPF v3 by the current Surfpool and LiteSVM
runtimes. `yarn test` first generates the IDL with Anchor, rebuilds the program
with `--arch v3`, and then runs `anchor test --skip-build`, ensuring that Anchor
does not overwrite the compatible binary before starting the test validator.

## Immutable beneficiary payout split

This project implements an immutable payout split that lets a campaign maker name a beneficiary and optionally reserve a transparent organizer fee when the fundraiser is created; if the campaign succeeds, the program atomically sends the configured fee to the maker and the remainder to the beneficiary, while a failed campaign charges no fee and preserves full contributor refunds. This benefits beneficiaries by making the promised allocation enforceable on-chain, contributors by letting them inspect the recipient and fee before donating, and legitimate organizers by compensating their work without taking custody of the beneficiary's share. A dishonest maker would try to increase the fee after contributions arrive, substitute a wallet they control for the advertised beneficiary, or pass forged payout accounts, so the program stores the beneficiary and fee immutably, caps the fee, and validates both recipients' token accounts during payout; the remaining social risk is that a maker can still advertise a misleading campaign or choose a beneficiary they secretly control, which contributors must detect from the public configuration.

### What it does

- The maker selects one beneficiary and a fee between 0 and 1,000 basis points
  (0% to 10%) when the campaign is initialized.
- The maker and beneficiary must be different addresses.
- Once the vault reaches the target, the maker can settle the campaign. The
  maker receives the configured fee and the beneficiary receives every
  remaining unit.
- Settlement uses the complete vault balance, including tokens above the target
  and tokens transferred directly to the vault.
- If the campaign expires below its target, contributors can recover their
  recorded contributions. No organizer fee is charged on a failed campaign.

The payout formulas use integer arithmetic:

```text
maker_fee          = floor(vault_balance * maker_fee_bps / 10_000)
beneficiary_amount = vault_balance - maker_fee
```

Rounding therefore favors the beneficiary. For example, with a vault balance
of `10,000,001` units and a 3% fee, the maker receives `300,000` and the
beneficiary receives `9,700,001`.

### How it works

The campaign-wide configuration lives in the fundraiser PDA. The two new fields
are appended at the end so the Borsh layout of the original fields is not
shifted:

```rust
#[account]
#[derive(InitSpace)]
pub struct Fundraiser {
    pub maker: Pubkey,
    pub mint_to_raise: Pubkey,
    pub amount_to_raise: u64,
    pub current_amount: u64,
    pub time_started: i64,
    pub duration: u8,
    pub bump: u8,
    pub beneficiary: Pubkey,
    pub maker_fee_bps: u16,
}
```

| Instruction           | Authorization and behavior                                                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `initialize`          | The maker signs, pays for the fundraiser PDA and vault, and supplies the immutable beneficiary and fee. It rejects `maker == beneficiary`, fees above 10%, and invalid targets.             |
| `contribute`          | A contributor transfers `mint_to_raise` tokens into the vault while the campaign is open. Per-transaction and cumulative contributions are limited to 10% of the target.                    |
| `check_contributions` | The maker triggers settlement when `vault.amount >= amount_to_raise`. The fundraiser PDA signs both token transfers and the fundraiser account closes to the maker only after both succeed. |
| `refund`              | After the deadline, and only while the vault is below the target, the fundraiser PDA returns the contributor's recorded amount and closes that contributor record.                          |

`check_contributions` validates the supplied beneficiary against the public key
stored in the fundraiser, binds `mint_to_raise` to the campaign's immutable mint,
and constrains both payout accounts to be the canonical associated token accounts
for that mint. The fee calculation uses checked multiplication, division, and
subtraction. Solana instructions are atomic, so a failure in the beneficiary
transfer also rolls back the maker transfer, any ATA created by the instruction,
and the fundraiser closure.

Successful settlement can only happen once: the fundraiser account is closed
after both transfers finish, so a second invocation cannot deserialize the
campaign account.

### What it costs

- The immutable split adds 34 bytes to the fundraiser data: a 32-byte
  beneficiary public key and a 2-byte fee. Including the original fields and
  Anchor's 8-byte discriminator, the fundraiser account allocates 132 bytes.
  The maker pays this additional rent once and recovers the fundraiser account's
  rent when a successful settlement closes it.
- Settlement accepts both the maker and beneficiary ATAs with
  `init_if_needed`. The maker pays to create whichever payout ATAs do not yet
  exist. Compared with the original single-recipient payout, the feature may
  create one additional 165-byte SPL Token account for the beneficiary.
- The successful path performs two SPL Token transfer CPIs instead of one, plus
  one checked multiplication, division, and subtraction. ATA creation, when
  needed, is the dominant additional compute cost. This assignment does not
  claim a fixed compute-unit figure because it varies depending on whether the
  payout ATAs already exist.
- The existing vault ATA is emptied but not closed, so its rent remains locked.
  That behavior is inherited from the base project and is not changed by this
  feature.

### How you would attack it

An attacker would first try to replace the advertised beneficiary or provide a
token account they control. The program prevents this with the stored
beneficiary address and Anchor's token-owner, mint, and associated-token
constraints. A malicious maker could also try to choose an excessive fee or
make themselves the beneficiary; initialization rejects both. Finally, an
attacker could force the second payout transfer to fail in the hope of leaving
the maker's fee paid, but instruction atomicity rolls the entire settlement
back.

The program cannot prove the real-world identity or intent behind a public key.
A maker may secretly control the advertised beneficiary, misrepresent the
campaign off-chain, or refuse to trigger settlement after the target is met.
That last case is a liveness risk: refunds are unavailable once the target is
met, while only the maker can settle. Front ends should prominently display the
beneficiary, fee, mint, target, and maker before accepting contributions.

The vault is a standard SPL Token account, so anyone can transfer the campaign
mint into it without calling `contribute`. Those direct transfers are included
in the target check and payout but are not recorded in `current_amount` or in a
Contributor account. For this assignment they are treated as anonymous
donations; in a production design, settlement and refund eligibility should use
a single program-controlled accounting source so an unsolicited transfer cannot
change the campaign outcome.

Token-2022 mints are intentionally out of scope; this program uses the
traditional SPL Token Program.

## Testing

```bash
# Build the SBPF v3 program and run the complete suite
yarn test

# Type-check the TypeScript tests
yarn tsc --noEmit

# Run only the payout feature tests
yarn test:payout
```

The payout suite covers the non-zero and zero-fee happy paths, integer rounding,
the exact target boundary, the maximum allowed fee, invalid beneficiaries,
forged beneficiary token accounts, forged campaign mints, and atomic rollback.
The time-window suite uses LiteSVM to advance the Clock sysvar and proves that an
expired campaign with a non-zero configured fee refunds the contributor without
paying the maker.
